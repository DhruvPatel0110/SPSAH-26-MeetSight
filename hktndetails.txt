1. HACKATHON OVERVIEW
============================================================

Title:
Stop Prompting. Code Solo Agents

Theme / Positioning:
The Dawn of the Autonomous AI Builder

Core idea:
The hackathon challenges solo developers to move beyond isolated prompts and wrapper scripts and build connected, autonomous agentic systems.

Participants are expected to build voice-first, memory-backed agentic workflows that can:
- Act
- Reason
- Persist information
- Operate in real time
- Coordinate multiple specialized agents
- Use persistent vector memory
- Connect voice input to agent reasoning and execution

The intended architecture combines:
- Omi for real-time voice capture / ambient input
- Qdrant for persistent vector memory and semantic retrieval
- Lyzr for multi-agent orchestration, reasoning, and task execution

7. MANDATORY CORE TECHNOLOGY STACK
============================================================

EVERY PROJECT MUST INTEGRATE ALL THREE:

------------------------------------------------------------
A. OMI
------------------------------------------------------------

Purpose:
Real-time voice capture and ambient input.

Role in the architecture:
- Captures spoken user input
- Provides the voice-first interaction layer
- Feeds voice/transcription information into the agent workflow

Key concept:
The project should demonstrate a real voice-to-agent workflow rather than only text input.

------------------------------------------------------------
B. QDRANT
------------------------------------------------------------

Purpose:
Persistent vector memory and semantic retrieval.

Role in the architecture:
- Stores embeddings / memories
- Retrieves semantically relevant information
- Enables persistent context across interactions
- Supports historical/contextual recall
- Can act as shared memory between agents

Key concept:
The application should demonstrate actual persistent memory rather than pretending to remember information inside a single prompt.

------------------------------------------------------------
C. LYZR
------------------------------------------------------------

Purpose:
Multi-agent orchestration, reasoning and task execution.

Role in the architecture:
- Coordinates specialized agents
- Delegates tasks
- Connects agent outputs
- Enables reasoning workflows
- Supports agent/task orchestration

Key concept:
The application should demonstrate an observable multi-agent execution workflow.

8. BUILD TRACKS / THEMES
============================================================

TRACK 1 — MEETING & LECTURE INTELLIGENCE

Description:
Build voice-to-insight systems that can process meetings or lectures and turn spoken information into useful structured intelligence.

Potential capabilities:
- Voice capture
- Transcript processing
- Semantic retrieval
- Automated action-item extraction
- Contextual Q&A about previous meetings
- Historical meeting recall
- Summarization
- Follow-up generation

Core idea:
Ask questions about what was discussed previously and retrieve relevant context from persistent memory.

------------------------------------------------------------

TRACK 2 — COLLABORATIVE MULTI-AGENT WORKFLOWS

Description:
Build voice-triggered execution pipelines where specialized agents coordinate with one another using a shared vector-memory layer.

Potential capabilities:
- Voice command
- Agent delegation
- Specialized agents
- Shared Qdrant memory
- Cross-agent communication
- Task decomposition
- DAG-style execution
- Automated actions

Core idea:
One spoken command can trigger multiple agents that collaborate to complete a task.

------------------------------------------------------------

TRACK 3 — PRIVACY-FIRST KNOWLEDGE SYSTEMS

Description:
Build secure and transparent memory architectures where users have granular control over what information is remembered and who/which agent can access it.

Potential capabilities:
- Local or semi-local memory
- User-controlled visibility
- Memory permissions
- Transparent memory inspection
- Memory deletion
- Selective retrieval
- Privacy controls

Core idea:
Persistent memory should not mean uncontrolled memory.

------------------------------------------------------------

TRACK 4 — ACCESSIBILITY & ADAPTIVE ASSISTANTS

Description:
Build voice-driven systems designed to make high-friction interfaces easier to use.

Potential capabilities:
- Voice-driven forms
- Guided workflows
- Structured output generation
- Accessibility assistance
- Voice commands for complex processes
- Adaptive user interaction

Core idea:
Use voice and agents to reduce friction for users who struggle with traditional interfaces.

------------------------------------------------------------

TRACK 5 — CONTINUOUS HEALTH & HABIT TRACKING

Description:
Build frictionless voice-based systems for daily logging, trend detection and time-aware semantic retrieval.

Potential capabilities:
- Daily voice logs
- Habit logging
- Temporal trend detection
- Historical retrieval
- Time-series semantic retrieval
- Personalized summaries
- Longitudinal context

Core idea:
Allow users to naturally record information over time and later ask questions about their history.

IMPORTANT:
Any health-related project should be designed responsibly and should avoid unsupported medical claims.

------------------------------------------------------------

TRACK 6 — OPEN INNOVATION

Description:
Wildcard applications across broad domains.

Suggested areas explicitly mentioned:
- DevTools
- Finance
- Automated research
- Gaming
- Autonomous operations

This track allows a project to apply the mandatory Omi + Qdrant + Lyzr architecture to another meaningful problem.

20. LOCAL MODEL / HARDWARE NOTES
============================================================

A local LLM is NOT inherently required by the hackathon description.

A practical implementation can use cloud/API-based AI services while:
- Omi handles voice capture
- Lyzr handles orchestration
- Qdrant handles vector memory
- A remote LLM/API handles model inference

This avoids requiring:
- Local GPU
- Ollama
- Large model downloads
- CUDA
- Multi-GB model files

Local models should only be introduced if required by the chosen architecture or if there is a specific reason to run inference locally.

============================================================
21. STORAGE / DEVELOPMENT NOTES
============================================================

The project itself should not require large local storage if cloud/API services are used.

Expected local project footprint:
- Source code: generally small
- Python/Node dependencies: moderate
- Frontend build/development files: moderate
- No mandatory multi-GB local LLM model
- Qdrant can be hosted remotely

A lightweight API-first implementation should be comfortable on a normal development laptop.
